Valheim 1.0 migration

Valheim 1.0 releases at 15:00 CEST / 9:00 AM EDT on September 9. Steam can replace the client assemblies automatically; we control when the dedicated server updates. The migration can take as long as it takes.

1. Preserve the current state

  • Back up: the stopped production world. This is the only essential data backup. The game's rolling and possible conversion backups are extra protection, not substitutes for ours.
  • Preserve for porting:
    • the pre-1.0 Mac client and Linux server game assemblies;
    • the matching BepInEx and mod binaries as reference inputs;
    • build IDs and hashes.

2. Prove vanilla 1.0 in disposable QA

  1. Make sure nobody is connected, then stop the server.
  2. Trigger one fresh world backup and R2 upload.
  3. Confirm it succeeded.
  4. Create a temporary Hetzner QA server.
  5. Install the exact 1.0 dedicated server build with mods disabled.
  6. Restore a disposable copy of the preserved world.
  7. Start the copied world on vanilla 1.0.
  8. Join with real characters, play, and save.
  9. Restart the server and rejoin.

If something fails, stop and investigate.

3. Convert production and restore mods in parallel

After vanilla QA passes, two independent lanes begin.

  • Production: install the exact vanilla server build proven in QA, open the untouched frozen production world, let 1.0 perform its own conversion, then join, play, save, restart, rejoin, and create a fresh R2 backup. Never promote the converted QA world.
  • QA: preserve and decompile the 1.0 client and server assemblies, compare them with pre-1.0, prove BepInEx and the standalone Valheim Dev bridge, then run and repair the existing mods. Independent failures go to agents in parallel; one integration lead tests each combined candidate.

Use the migration task for assignments and decisions, and Axiom as the single searchable surface for actionable failures. Keep candidate binaries and hashes together; retain local NDJSON, BepInEx logs, and the systemd journal as raw fallbacks.

Promote only the exact mod binaries and configuration that passed QA.

Fix forward from observed failures. If an existing mod still works, leave it alone. Each failure must identify the mod area and include the exception or failed target when available. The disposable QA server is the fast iteration environment; mod work never mutates production.

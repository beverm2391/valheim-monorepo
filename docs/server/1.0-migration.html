Valheim 1.0 migration

Preserve the current state → prove vanilla 1.0 in disposable QA → port mods in parallel → promote the proven build.

Valheim 1.0 releases at 15:00 CEST / 9:00 AM EDT on September 9. Steam can replace the client assemblies automatically; we control when the dedicated server updates. The migration can take as long as it takes.

1. Preserve the current state

  • Back up: the stopped production world. This is the only essential data backup. The game's rolling and possible conversion backups are extra protection, not substitutes for ours.
  • Preserve for porting:
    • the pre-1.0 Mac client and Linux server game assemblies;
    • the matching BepInEx and mod binaries as reference inputs;
    • build IDs and hashes.

2. Prove vanilla 1.0 in disposable QA

  1. Make sure nobody is connected, then stop the server.
  2. Trigger one fresh world backup and R2 upload.
  3. Confirm it succeeded.
  4. Create a temporary Hetzner QA server.
  5. Install the exact 1.0 dedicated server build with mods disabled.
  6. Restore a disposable copy of the preserved world.
  7. Start the copied world on vanilla 1.0.
  8. Join with real characters, play, and save.
  9. Restart the server and rejoin.

If something fails, stop and investigate.

3. Port mods and promote the proven build

  1. Preserve and decompile the 1.0 client and server assemblies.
  2. Compare the decompiled pre-1.0 and 1.0 client and server source.
  3. Use the comparison to identify the changes relevant to each mod area.
  4. Prove BepInEx and the standalone Valheim Dev bridge by themselves.
  5. Run all existing mods together on QA before rewriting them.
  6. Capture compilation, plugin-load, Harmony patch, runtime, and gameplay failures.
  7. Give independent failures to agents working in parallel.
  8. Use the migration task for assignments and decisions, and Axiom as the single searchable surface for actionable failures. Keep candidate binaries and hashes together; retain local NDJSON, BepInEx logs, and the systemd journal as raw fallbacks.
  9. Have one integration lead install and test them on QA.
  10. Promote only the exact passing binaries and configuration to production.
  11. Join production, play, save, restart, and rejoin.

Fix forward from observed failures. If an existing mod still works, leave it alone. Each failure must identify the mod area and include the exception or failed target when available. The disposable QA server is the fast iteration environment; production remains untouched until the build is proven.
